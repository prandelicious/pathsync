Question 5: How should failures appear in the final summary?

Failures need to be obvious, but not so loud that they obscure what succeeded.

Target Results
Target      Planned   Copied   Verified   Copy Fail   Verify Fail   Result
T7              159      159        159           0             0    ok
Archive         159      157        157           1             1    attention

Failures
Target    Phase    File                  Error
Archive   verify   GX010193.MP4          signature mismatch
Archive   copy     GX010194.MP4          permission denied

A. Inline Status + Failure Table

Target rows show attention status, then a nearby failure table gives exact file, phase, and error.

Attention
Archive had 2 failed items:
copy failed: GX010194.MP4 - permission denied
verify failed: GX010193.MP4 - signature mismatch

Target Results
T7       159/159 verified
Archive 157/159 verified

B. Failure Narrative First

Lead with a human-readable problem statement, then show target results below.

Target Results
Target      Planned   Copied   Verified   Copy Fail   Verify Fail
T7              159      159        159           0             0
Archive         159      157        157           1             1

Failures are written to:
/tmp/pathsync-run-20260503-001/errors.log

C. Summary Only + External Log

Keep terminal clean and point to a detailed failure artifact.

My recommendation: A

  • It preserves the target verification table as the main truth source.
  • The failure table is machine-scannable and actionable: target, phase, file, error.
  • It works in terminal scrollback without requiring a separate artifact.

Tradeoff

  • Long failure lists need a preview limit plus a clear “showing N of M” line.
